# ApplyForge Architectural Overview

This document serves as the high-level map of the ApplyForge system, detailing its components, data flows, and structural invariants.

## Core System Philosophy

ApplyForge functions as an end-to-end job hunt operating system. It moves the user from initial resume ingestion through job discovery, scoring, document tailoring, and finally to automated application execution.

A central tenet governs the entire architecture: **The canonical candidate profile is the absolute source of truth.** All downstream outputs (tailored resumes, cover letters, application answers) are generated by selecting, emphasizing, and formatting facts derived exclusively from this profile. The system is strictly forbidden from fabricating experience or skills.

## Architectural Boundaries

The application is organized as a monorepo containing distinct operational domains:

### 1. `apps/api` (FastAPI + SQLAlchemy)
This is the central nervous system. It handles:
- User authentication and session management.
- CRUD operations for the candidate profile and document uploads.
- Job normalization, routing, and algorithmic scoring.
- Prompt generation and LLM orchestration for document tailoring.
- Application state management via a strict Finite State Machine (FSM).
- Exposing the REST interface consumed by the web client.

### 2. `apps/web` (Next.js + TypeScript)
The operator's control panel. It provides interfaces for:
- Marketing and user onboarding.
- Dashboard analytics and the job feed.
- Profile editing and resume template selection.
- Target role configuration and pipeline tracking.
- System diagnostics and manual override controls.

### 3. `apps/worker` (Celery + Playwright)
The asynchronous execution engine. It handles:
- Heavy background tasks like web scraping for job enrichment.
- Browser-based execution of job applications via Playwright.
- Capturing forensic evidence (screenshots) and halting at pre-defined pause gates (e.g., CAPTCHAs, missing OTPs).

### 4. `packages/config`
A registry for structured product data:
- Pre-defined discovery configurations (employer sources, common search templates).
- Default resume assets (Markdown and LaTeX starter templates).

Additional context files reside in `docs/` and agent-specific guidelines are maintained in `.agents/` and `.codex/`.

## Logical Subsystems

The architecture is divided into the following operational domains:

### 1. Identity & Access
- Handles cookie-based JWT authentication.
- Enforces strict user-level data isolation.
- Implements rate limiting on critical endpoints (login, OTP requests).

### 2. The Candidate Brain
- Manages resume parsing from PDF, DOCX, and TXT files.
- Structures data into specific domains (skills, experience, projects, education).
- Exposes user preferences (automation policies, saved answers) as a portable configuration object.

### 3. Document Rendering Pipeline
- Supports multiple ATS-optimized themes.
- Generates outputs via a structured RenderCV builder, with a fallback PDF rendering mechanism if RenderCV fails.
- Allows users to preview source code (Markdown/LaTeX) before compilation.

### 4. Discovery & Enrichment Engine
- Driven by `target_roles` which define keywords, aliases, and automation thresholds.
- Scrapes external sources and deduplicates incoming jobs.
- Dispatches raw job descriptions to the asynchronous worker for deeper data extraction.
- Publishes lifecycle events (discovered, enriched, expired) to the job feed.

### 5. Company Intelligence Graph
- Maps normalized job postings to canonical company identities.
- Stores recruiter contact information and company-specific career portal metadata to aid future automations.

### 6. Scoring & Content Tailoring
- Evaluates enriched jobs against the candidate's canonical profile.
- Produces a transparent score detailing strengths, missing skills, and a final recommendation.
- Generates a tailored resume variant by strategically emphasizing existing profile facts.

### 7. Application State Machine
- Prepares a formal "application packet" (resume, cover letter, resolved answers) before attempting an application.
- Governs application runs via an explicit FSM with states: `queued`, `running`, `paused`, `failed`, `completed`, and `uncertain`.

### 8. Worker Execution & Forensics
- The `RunRecorder` actively logs every step of a browser automation attempt to the shared database.
- Saves browser screenshots directly to file storage.
- Implements specific field adapters (text, select, radio) and graceful failure mechanisms (e.g., pausing when encountering unsupported inputs or anti-bot defenses).

### 9. Inbox Integration & OTP Handling
- Integrates with Gmail and Outlook via OAuth.
- Retrieves OTP codes necessary for completing specific application flows.
- Masks sensitive codes in the database logs and gracefully pauses the application run if an OTP cannot be securely retrieved.

## Key Data Models

The primary SQLAlchemy entities include:
- `users`, `candidate_profiles`, `resumes`, `resume_versions`, `resume_themes`
- `jobs`, `job_scores`, `job_sources`, `target_roles`, `target_role_sources`
- `job_ingestion_runs`, `job_feed_events`
- `companies`, `company_career_portals`, `company_contacts`
- `applications`, `application_runs`, `application_steps`
- `inbox_connections`, `inbox_otp_events`, `uploaded_files`

## Operational Safety Protocols

ApplyForge is designed to fail gracefully and securely:
- **No Hallucinations:** Tailoring algorithms are restricted from inventing qualifications.
- **Approval Gates:** High-risk application questions (e.g., salary expectations, visa status) force a manual pause.
- **Bot Detection Compliance:** Encounters with CAPTCHAs pause the automation rather than attempting evasive bypass techniques.
- **Durable Evidence:** If a worker crashes, the partial execution steps and screenshots remain accessible via the diagnostic UI.
- **Secret Masking:** OAuth tokens and OTPs are heavily sanitized before being written to logs or returned via the API.

## Baseline Verification Checks

When modifying the system, ensure the following commands complete successfully:

```bash
# Python Compilation Check
python3 -m compileall apps/api/app apps/api/tests apps/worker/app apps/worker/tests

# Backend API Tests
PYTHONPATH=/tmp/applyforge-pydeps:apps/api python3 -m pytest apps/api/tests -q

# Worker Task Tests
PYTHONPATH=/tmp/applyforge-pydeps:apps/worker DATABASE_URL=sqlite+pysqlite:///:memory: REDIS_URL=redis://localhost:6379/0 python3 -m pytest apps/worker/tests -q

# Frontend Checks
cd apps/web
npm run lint
npm run build
npm run typecheck
```
*(Note: Always run Next.js `typecheck` after `build` to ensure generated types are present.)*
